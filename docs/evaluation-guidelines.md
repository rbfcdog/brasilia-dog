# NextWave Hackathon 2026 evaluation guidelines

_How the jury evaluates projects and runs the judging session._

---

## Three principles

| Principle | Meaning |
| --- | --- |
| Depth over difficulty | Selecting the hardest challenge does not earn points by itself. A modest scope solved deeply is stronger than an ambitious but shallow system |
| Working over promised | The jury evaluates what runs live, not what slides claim will run |
| Judgment over spectacle | Technical defense carries as much weight as the demo. Teams need to explain their choices and rejected alternatives |

## Jury lenses

The jury uses five lenses. They are listed in rough order of weight, but no one lens decides a winner.

| Lens | Jury question |
| --- | --- |
| 1. Does it work? | Does the system run from start to finish and pass trial by fire when judges change something live without team help? |
| 2. Depth and judgment | Is the architecture sound? Can the team explain major decisions, rejected alternatives, and trade-offs in the decision log? |
| 3. Solves the real problem | Does the system meet the selected brief, including ugly cases, instead of building a nearby generic product? |
| 4. Originality | Does the project have a distinct idea, mechanism, or insight beyond an obvious solution? |
| 5. Experience and clarity | Would a person use it? Is the pitch clear, demo legible, and repository readable by someone who was not there? |

## Judging session

| Step | Detail |
| --- | --- |
| Presentation | Each team gives a short pitch |
| Demonstration | The team shows the working prototype live |
| Trial by fire | Judges introduce an unrehearsed input or change and observe the system response |
| Technical Q&A | Judges ask about the architecture and decisions |
| Ranking | The full panel sees every project. Judges rank independently before deliberating together |

The standard slot is 10 minutes. City champions later give a 15-minute final pitch, with 10 minutes for the presentation and 5 minutes for questions.

## What does not score

- Number of features, slides, integrations, or lines of code
- Buzzwords or framework names without a reason for choosing them
- A polished video for a system that does not run live
- A project built one rubric item at a time without a coherent solution to the selected problem

## Practical advice from the brief

Get a thin end-to-end version working in the first hours. Then use the remaining time to cover ugly cases, understand the trade-offs, and rehearse the live change a judge may make. Teams that start with a polished frontend can run out of time before the core system works.
